# Check linked merge requests without changing work reports

In **Connections → GitLab evidence**, enter your GitLab HTTPS URL and a token with `read_api` access, preferably scoped to the relevant project. The host is configurable: GitLab.com and company-hosted GitLab use the same adapter. Hostnames and tokens are installation data, not product defaults or repository content. The first version supports one configured GitLab origin per Mac.

Saving access stores it in protected local application storage; it does not claim the token has been verified. Link an MR as a change output through the normal agent workflow, then select that change and choose **Check GitLab** beside the output. The app only makes `GET` requests for that explicitly linked MR. It does not crawl projects, modify GitLab, follow redirects, or send access credentials to a different host. The same check is available to agents through `check_output` with the exact work/output IDs and output revision; `get_work` with `part=output-evidence` reads saved evidence. Reload the MCP connection to see new tool schemas. GitLab access does not change existing agent/feedback permissions.

The inspector and change details keep two separate facts:

- **Reported evidence:** the actor's output state, timestamp and code revision.
- **GitLab observation:** MR state, matching head pipeline status, draft/mergeability, conflicts, blocking-discussion status, checked time and observed revision. Missing fields stay unknown; GitLab’s asynchronous mergeability check is never treated as confirmed absence of conflicts.

Checks are snapshots, not live guarantees. An edited output or different pinned code revision makes an older observation historical. Failed/unavailable checks retain a safe category and HTTP status when available, with fixed next steps for authentication, permission, not-found/moved projects, rate limits, redirects, timeouts and network/certificate failures. Provider response bodies and raw exceptions are not retained. These failures do not overwrite the output report. Output edits, disconnected/replaced access and revoked agent credentials during a request cause that response to be discarded. Observations cannot mark a change delivered, satisfy its existing reported integration gate, answer a human request, or add daily completion credit.

Agents should check at meaningful MR review/delivery milestones and after relevant pushes when MR evidence matters. There is no prompt-by-prompt or background polling and no project-specific script invocation. No combination of green fields guarantees merge readiness or grants permission to merge.

Access can be updated or removed in Connections. New app-managed access on macOS stores the token in Keychain, through a bundled native bridge using Apple's Security framework. The private app configuration contains only its reference. Tokens travel to that bridge over stdin, never process arguments or environment variables. Keychain denial/unavailability is reported without silently creating a plaintext file. Existing private token-file configurations remain readable and migrate to Keychain when access is explicitly updated. Other platforms retain protected-file storage. Tokens are never returned by the API, stored in work records or browser persistence, or included in installer artifacts. Keychain secrets are separate from application-data backups; on another Mac, configure access again. Removing local access does not revoke the token at GitLab; revoke it there when appropriate.

Administrators can instead set `RHEO_GITLAB_CONFIG` to an absolute private JSON file containing `origin` and an absolute `tokenFile` reference. Both files must be private regular files outside any repository; file permissions alone do not prevent commits. `tokenFile` contains only the token. An externally managed configuration is read-only in Connections. Use an HTTPS origin such as `https://gitlab.example.com` without a path, query or embedded credentials.

The local workflow helper's `evidence --binding BINDING --session-id SESSION` reads the selected change's evidence. Add `--output-id OUTPUT_ID` to check that specific MR using the same configured adapter. The low-level output-reporting APIs remain unchanged. Other hosting providers and multiple simultaneous GitLab access profiles can be added without changing graph or delivery semantics.

References: [GitLab merge requests API](https://docs.gitlab.com/api/merge_requests/), [GitLab REST authentication](https://docs.gitlab.com/api/rest/authentication/).
